# Decisions

Each entry records what was chosen, the alternatives considered and why. Add a new entry
whenever a choice affects more than one crate or would surprise a newcomer.

## 001 — Engine: Bevy 0.19

- **Alternatives:** Fyrox, raw `wgpu` + `winit`.
- **Why:** Bevy's ECS and plugin model map directly onto a modular architecture, it has the
  most active Rust ecosystem, loads glTF with skeletal animation and blends clips through its
  animation graph. Fyrox is more editor-centric; raw wgpu would mean writing an engine.
- **Consequence:** Bevy has breaking releases every few months. Upgrades are done in one
  commit per Bevy version together with Avian and bevy_enhanced_input.

## 002 — Cargo workspace with one crate per feature

- **Alternatives:** a single crate with one module per feature.
- **Why:** crate boundaries enforce the dependency direction, keep incremental compiles fast
  (only changed crates rebuild) and make features easy to add, remove or reuse.
- **Convention:** crates are named `gf_<feature>` and expose exactly one `Plugin`.

## 003 — Physics: Avian 3D with a kinematic character controller

- **Alternatives:** `bevy_rapier3d`, no physics.
- **Why:** Avian is ECS-native and ships `MoveAndSlide`, a collide-and-slide solver for
  kinematic characters. Kinematic control gives precise, predictable movement (no sliding,
  no bouncing) and full control over crouch, slopes and ground snapping.
- **Details:** walkable slopes up to 45°; steeper surfaces are treated as walls. Stairs are
  not handled yet (see the scaling guide).

## 004 — Input: bevy_enhanced_input

- **Alternatives:** leafwing-input-manager, a custom action layer.
- **Why:** actions are decoupled from devices, and *contexts* (`Gameplay`, `Menu`) are turned
  on and off automatically from `PauseState`. Rebinding and gamepads come for free.
- **Details:** `Pause` and `Back` share the Escape key; `require_reset` prevents the same key
  press from opening and immediately closing the menu.

## 005 — Controls

WASD to move, Shift (hold) to run, Ctrl (hold) to crouch, mouse to look, Esc to pause.
Gamepad bindings mirror them. Five locomotion states: Idle, Walk, Run, CrouchIdle, CrouchWalk.

## 006 — Character faces its movement direction

- **Alternative:** always face the camera direction (shooter style strafing).
- **Why:** adventure-style movement only needs forward cycles, keeping the animation set
  small. Strafing can be added later with directional clips and a blend space.

## 007 — Orbit camera with spring arm collision

The camera orbits a pivot above the player, clamps pitch, sphere-casts against `World`
geometry and snaps closer instantly when blocked, easing back out afterwards. The pivot
height follows the stance smoothly so crouching lowers the view.

## 008 — Animation: named clips, crossfades and playback-speed sync

- **Alternatives:** fixed crossfade only.
- **Why:** transitions are defined per clip pair (`Transitions::between`), locomotion cycles
  keep their normalized phase when switching (`sync_phase`), and playback speed follows the
  real ground speed divided by each clip's reference speed, which removes foot sliding.
- **Details:** built on `AnimationGraph` + `AnimationTransitions`. `gf_animation` knows
  nothing about players; any entity with an `Animator` works.

## 009 — Placeholder humanoid generated by a Blender script

- **Alternatives:** a CC0 asset pack, Mixamo.
- **Why:** fully reproducible, no licensing issues, and the output is a normal `.blend` that
  can be edited by hand. `tools/blender/generate_player.py` builds a 20-bone rig, a
  ~1.3k-triangle rigidly skinned body and five in-place clips.
- **Consequence:** the look is a stylized mannequin. Replace it by exporting any humanoid
  whose action names match the clip names (see the asset pipeline doc).

## 010 — Levels are authored in Blender too

Every 3D asset lives in `assets/` as a `.blend` source plus an exported `.glb`. Level meshes
become static trimesh colliders automatically, and empties named `PlayerSpawn*` become spawn
points, so level design needs no code changes.

## 011 — Blender → Bevy coordinate conversion

`GltfPlugin::convert_coordinates.rotate_scene_entity` is enabled so that Blender's front
view (-Y) maps to Bevy's forward (-Z). Models are authored facing -Y as Blender expects.

## 012 — Minimum hardware: DX12/Vulkan GPUs, `Low` preset by default

- **Alternative:** an OpenGL fallback for very old GPUs.
- **Why:** DX12/Vulkan covers any integrated GPU from roughly 2014 onward without the
  complexity and feature limits of the GL backend. See the performance doc for the
  optimizations applied.

## 013 — Loading state instead of a loading crate

A tiny `LoadingQueue` in `gf_core` replaces `bevy_asset_loader`, avoiding another dependency
that must track every Bevy release.

## 014 — Engine features trimmed

Bevy is compiled with only the `3d` and `ui` feature collections (no 2D, no audio), which
reduces compile time and binary size. Add `"audio"` to the workspace Bevy features when sound
is needed.

## 015 — Build configuration

- `opt-level = 1` for our code and `3` for dependencies in dev builds: debug builds run
  smoothly while our crates still compile fast.
- Release uses fat LTO, one codegen unit, `panic = "abort"` and stripped symbols.
- `rust-lld` is used as the linker on Windows for faster links.
- The `dev` feature enables Bevy dynamic linking for much faster iterative builds.
- `.cargo/config.toml` sets `BEVY_ASSET_ROOT` so `cargo run` finds the workspace `assets/`
  folder; shipped builds look for `assets/` next to the executable.

## 016 — Git conventions

Short, atomic commits on `main` with a bracketed tag: `[ADD]`, `[FIX]`, `[UPDATE]`,
`[REMOVE]`, `[REFACTOR]`, `[DOCS]`. Example: `[ADD] Crouch state`. See the contributing doc.

## 017 — Character controller split from the player

The kinematic controller lives in `gf_character` and is driven only by `MoveIntent`.
`gf_player` is a thin layer that turns input into intents and locomotion into animation, so
NPCs, AI and networked characters reuse the exact same movement code.

## 018 — Persistent settings, one RON file per group

- **Alternatives:** a single settings file with every section, no persistence.
- **Why:** each crate owns its settings resource and registers it with
  `register_settings::<T>("name")`; `gf_settings` loads `<config dir>/game-foundation/name.ron`
  at startup and rewrites it whenever the resource changes. One file per group avoids a
  central type that knows every crate, and a corrupt file only resets that group.
- **Location:** `%APPDATA%\game-foundation\` on Windows, `~/.config/game-foundation/` on Linux,
  `~/Library/Application Support/game-foundation/` on macOS.

## 019 — Graphics settings: preset plus individual options

The Graphics tab offers a preset (Low, Medium, High) and individual options for shadows
(Off, Low, Medium, High), anti-aliasing (Off, FXAA, MSAA 4x) and vsync. Choosing a preset
overwrites the options; changing an option shows the preset as *Custom*. Only the options are
stored, the preset is derived from them. Changes apply immediately.

## 020 — Tabbed pause menu

The pause menu has tabs (Game, Graphics). Every button carries a `MenuAction` component and
a single system handles presses, so new tabs and options are data, not new systems.
